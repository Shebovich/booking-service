# День 4. PostgreSQL: SQL, индексы, транзакции — конспект для повторения

Конспект по официальной документации PostgreSQL 18 и нашим опытам (`sql/explain-lab.sql`, `sql/transactions-lab.sql`).
Проще, но полностью — чтобы повторить перед собеседованием.

---

## 1. Зачем бэкенду Postgres и чем он отличается от SQLite/Room

- В Android база — **файл внутри приложения** (SQLite), с ней работает один процесс, пользователь один.
- На бэкенде база — **отдельный сервер**: к нему одновременно подключаются десятки экземпляров сервиса и тысячи запросов.
  Отсюда главные темы дня: **скорость при больших данных** (индексы) и **одновременная работа** (транзакции).
- Postgres мы запускаем в **Docker**:
  - *образ* (image) — «APK»: шаблон, из которого запускают;
  - *контейнер* — «запущенное приложение» из образа;
  - *порт* `5432:5432` — дверь из контейнера наружу, на твой компьютер;
  - *volume* — папка с данными вне контейнера. Контейнер можно удалить и пересоздать, данные останутся
    (как база Room переживает перезапуск процесса).
  - Контейнер не поднимается сам после падения Docker, если не указать `restart: unless-stopped` в `compose.yaml`.

## 2. SQL: как пишется и в каком порядке выполняется запрос

### Порядок выполнения SELECT

Пишем в одном порядке, а база выполняет в другом:

1. `FROM` / `JOIN` — какие таблицы и как склеить;
2. `WHERE` — отфильтровать **строки**;
3. `GROUP BY` — собрать строки в группы;
4. `HAVING` — отфильтровать **группы**;
5. `SELECT` — посчитать колонки, дать псевдонимы;
6. `ORDER BY` — отсортировать;
7. `LIMIT` / `OFFSET` — отрезать.

Следствия, которые спрашивают:
- в `WHERE` нельзя использовать псевдоним из `SELECT` и агрегаты (`count`, `sum`) — их ещё не посчитали; для агрегатов есть `HAVING`;
- в `ORDER BY` псевдоним из `SELECT` использовать можно — он уже посчитан.

### JOIN

- `INNER JOIN` — только пары, у которых нашлась пара в обеих таблицах.
- `LEFT JOIN` — все строки левой таблицы; если пары справа нет, справа подставляется `NULL`.
- **Self-join** — таблица соединяется сама с собой (участник и тот, кто его порекомендовал, — оба в `members`).
- Ловушка LEFT JOIN: условие на правую таблицу в `WHERE` выкидывает строки с `NULL` и превращает LEFT JOIN в INNER.
  Если нужно «все участники, плюс их брони за сентябрь, если есть» — условие на дату пишут в `ON`, а не в `WHERE`.

### GROUP BY и агрегаты

- `GROUP BY` превращает много строк в одну на группу; `count`, `sum`, `avg`, `max`, `min` считают по группе.
- В `SELECT` можно писать только колонки из `GROUP BY` и агрегаты.
- `count(*)` считает строки, `count(колонка)` — только строки, где колонка **не NULL**.
  После LEFT JOIN это важно: у участника без броней `count(*)` = 1 (строка с NULL справа), а `count(b.bookid)` = 0.

### NULL

- `NULL` — «неизвестно», а не ноль и не пустая строка.
- `NULL = NULL` — это не `true`, а снова `NULL`. Проверять только через `is null` / `is not null`.
- Агрегаты (кроме `count(*)`) пропускают NULL.

### Подзапросы

- **Скалярный** — возвращает одно значение, можно подставить как число: `where joindate = (select max(joindate) ...)`.
- **Коррелированный** — ссылается на внешнюю строку и логически выполняется для каждой из них.
  Удобно, но на больших таблицах часто медленнее JOIN.

### Прочее, что встречалось

- `UNION` убирает дубли (значит, сортирует или хеширует — дороже), `UNION ALL` просто склеивает.
- Деление целых чисел даёт целое: `5 / 2 = 2`. Нужна дробь — привести к `numeric`.
- `ORDER BY ... LIMIT 1` при одинаковых значениях вернёт **случайного** из равных. Для стабильного результата
  добавляют второй ключ сортировки, обычно `id`: `order by check_in, id`. То же правило для пагинации.
- **Оконные функции** (`row_number()`, `rank()`, `dense_rank()` + `over (partition by ... order by ...)`) считают
  значение для каждой строки, не схлопывая их, в отличие от `GROUP BY`. Фильтровать по ним в `WHERE` нельзя
  (они считаются на шаге SELECT) — оборачивают в подзапрос.
  - `row_number`: 1, 2, 3, 4 — всегда разные;
  - `rank`: 1, 2, 2, 4 — одинаковым одно место, потом пропуск;
  - `dense_rank`: 1, 2, 2, 3 — без пропуска.

## 3. Как Postgres выполняет запрос

1. **Парсер** — проверяет синтаксис, строит дерево запроса.
2. **Планировщик** — SQL говорит *что* получить, но не *как*. Планировщик перебирает варианты
   (таблица целиком или индекс, какой JOIN, в каком порядке), считает **стоимость** каждого и выбирает самый дешёвый.
3. **Исполнитель** — выполняет план.

Планировщик опирается на **статистику**: сколько строк, какие значения частые, как распределены.
Её собирает `ANALYZE` (сам — в фоне через autovacuum). Устаревшая статистика → плохой план → «запрос внезапно стал медленным».
Аналогия: навигатор строит маршрут по данным о пробках; данные устарели — маршрут плохой.

## 4. Индексы

### B-tree — индекс по умолчанию

- **Отсортированное дерево**: корень → промежуточные узлы → листья. В листьях — значение и **адрес строки** в таблице.
- Поиск — как бинарный поиск: на миллион строк 3–4 шага. В опыте 1 чтение одной брони по email
  стоило **4 страницы** вместо **11 249**: 3 на спуск по дереву + 1 сама строка.
- Из-за сортировки B-tree умеет `=`, `<`, `>`, `between`, `order by`, `LIKE 'начало%'`.
- Аналогия: алфавитный указатель в конце книги.

### Способы чтения таблицы (узлы в EXPLAIN)

- **Seq Scan** — прочитать всю таблицу подряд. Последовательное чтение быстрое; если нужна большая часть таблицы — это лучший вариант.
  **Parallel Seq Scan** + **Gather** — то же самое в несколько процессов, Gather собирает результат.
- **Index Scan** — нашли адреса в индексе, по каждому сходили в таблицу. Хорошо, когда строк мало.
- **Bitmap Index Scan + Bitmap Heap Scan** — для «средне много» строк: собрали все адреса, отсортировали по расположению
  на диске и прочитали таблицу за один проход без прыжков. `Recheck Cond` — перепроверка условия на прочитанных строках.
- **Index Only Scan** — все нужные колонки есть в индексе, в таблицу можно не ходить (условие — см. раздел 5).

### Селективность — главное понятие

- Селективность — какую долю таблицы вернёт условие.
- Индекс выгоден только для **селективных** условий. Иначе прыжки «индекс → таблица» дороже, чем прочитать всё подряд.
- Опыт 5: индекс на `status` есть, но для `CONFIRMED` (90% строк) Postgres выбрал Seq Scan — и правильно.
  Даже для `CANCELLED` (5%) выигрыш всего ×3: 50 тыс. строк разбросаны почти по всем страницам таблицы.
- Индекс на колонку с 2–3 значениями почти всегда бесполезен. Если часто ищут **редкое** значение — делают
  **частичный индекс**: `create index ... on bookings (created_at) where status = 'PENDING'`.

### Когда индекс НЕ используется (наши опыты)

1. **Функция над колонкой** (опыт 2): индекс хранит `guest_email`, а ищем `lower(guest_email)` — это другие значения.
   Решение — **индекс по выражению**: `create index ... on lab_bookings (lower(guest_email))`. Выражение должно совпадать с WHERE.
2. **LIKE с процентом в начале** `'%7777@mail.test'` (опыт 3): индекс отсортирован с начала строки, искать по концу нельзя.
   Для таких поисков есть расширение `pg_trgm` с другим типом индекса.
3. **LIKE по началу при collation не «C»** (опыт 3): база сравнивает строки по правилам языка (`en_US.utf8`),
   и Postgres не может превратить `LIKE 'abc%'` в диапазон. Решение — класс операторов
   `text_pattern_ops`: `create index ... on lab_bookings (guest_email text_pattern_ops)` — сравнение посимвольно.
   В плане видно, как LIKE превратился в диапазон `~>=~ 'guest77777' AND ~<~ 'guest77778'`.
4. **Неселективное условие** (опыт 5) — см. выше.
5. **Несовпадение типов** (например, сравнение числовой колонки со строкой с приведением колонки) — по той же причине, что и функция.

### Составной индекс и порядок колонок

- Индекс `(room_id, check_in)` отсортирован сначала по `room_id`, внутри — по `check_in`. Как телефонная книга «город → фамилия».
- **Правило левого префикса**: индекс эффективен для условий на `room_id`, на `room_id + check_in`, для `order by room_id, check_in`.
- Условие только на `check_in` — классически индекс не работает. Но в **Postgres 18 появился skip scan**: база по очереди
  «прыгает» в раздел каждого `room_id` и ищет там нужную дату. В опыте 4 — `Index Searches: 501`: около 500 прыжков
  (по одному на каждый номер). Выгодно, только когда в первой колонке **мало разных значений**.
- Как выбирать порядок колонок: сначала колонка с условием `=`, потом колонка с диапазоном (`between`, `>`) или сортировкой.
  Условие `=` по первой колонке и диапазон по второй читаются одним непрерывным куском индекса.

### Цена индексов (опыт 7)

- **Место**: таблица 88 MB, три индекса ≈ 39 MB; один индекс на email — 39 MB, почти половина таблицы.
- **Память**: индексы занимают кэш (shared buffers) и вытесняют оттуда данные.
- **Запись**: каждый `INSERT` обновляет **все** индексы таблицы. `UPDATE` колонки из индекса тоже обновляет индексы.
- **VACUUM и планировщик**: больше работы и больше вариантов перебора.
- Правило: индекс — под конкретный медленный запрос, а не «на всякий случай». Неиспользуемые ищут по
  `pg_stat_user_indexes.idx_scan = 0`.

### Как читать EXPLAIN

- `EXPLAIN` — план и **оценки**, запрос не выполняется.
  `EXPLAIN ANALYZE` — **выполняет** запрос и показывает реальные цифры. Осторожно с UPDATE/DELETE: они реально изменят данные
  (оборачивать в `begin; ... rollback;`).
- `cost=0.42..8.44` — условная стоимость: до первой строки..до последней. Не миллисекунды, сравнивать только планы между собой.
- `rows=` в первых скобках — сколько строк **ожидает** планировщик; `actual ... rows=` — сколько было **на самом деле**.
  Сильное расхождение — главный признак проблемы (обычно статистика). В опыте 2 ожидалось 5000, реально 1.
- `loops` — сколько раз выполнялся узел (у параллельных — по числу процессов).
- `Rows Removed by Filter` — сколько строк прочитано зря.
- `Buffers: shared hit / read` — страницы по 8 КБ: `hit` — из памяти, `read` — с диска. В PG18 показывается в EXPLAIN ANALYZE сам.
- `Index Searches` (новое в PG18) — сколько раз спускались по дереву индекса.
- `Heap Fetches` (у Index Only Scan) — сколько раз всё-таки пришлось сходить в таблицу.
- Читать план **изнутри наружу**: самый вложенный узел выполняется первым.

### Алгоритм «запрос тормозит» (частый вопрос)

1. Найти медленный запрос: логи медленных запросов, расширение `pg_stat_statements`.
2. `EXPLAIN (ANALYZE)` на реальных данных: где Seq Scan по большой таблице, где расходятся `rows` ожидаемые и реальные,
   где много `Rows Removed by Filter`, где `read` с диска.
3. Проверить статистику (`ANALYZE`) и вздутие таблицы (bloat) после массовых UPDATE/DELETE.
4. Добавить/исправить индекс под условие: порядок колонок, выражение, частичный индекс.
5. Переписать запрос: убрать функции над колонкой, `select *` → нужные колонки, OFFSET → keyset-пагинация.
6. Проверить, что запрос не вызывается N раз в цикле из кода (проблема **N+1** — будет на дне 5 с JPA).

Про пагинацию: `OFFSET 100000` заставляет базу прочитать и выбросить 100 тыс. строк. Быстрее **keyset**:
`where (check_in, id) > (:последний_check_in, :последний_id) order by check_in, id limit 20` — сразу прыжок по индексу.

## 5. MVCC и VACUUM

- **MVCC** (многоверсионность): Postgres не перезаписывает строку на месте. `UPDATE` = старая версия помечается мёртвой,
  рядом пишется новая. `DELETE` = версия помечается мёртвой.
- Зачем: каждая транзакция видит **свой снимок** данных, поэтому **читатели не блокируют писателей и наоборот**.
  Аналогия: git — изменение = новый коммит, старый остаётся в истории.
- Минус: мёртвые версии копятся — таблица и индексы «пухнут» (**bloat**), запросы читают лишнее.
- **VACUUM**:
  1. убирает мёртвые версии и освобождает место для новых строк (файл таблицы при этом не уменьшается);
  2. проставляет биты в **visibility map** — «на этой странице все строки видны всем».
- **Autovacuum** делает это сам в фоне. Если он не успевает (очень много UPDATE) — bloat и замедление.
- **Index Only Scan и visibility map** (опыт 6): в индексе нет информации, жива ли версия строки. Если страница
  не отмечена как «вся видимая», приходится идти в таблицу (`Heap Fetches`).
  - Свежая таблица: карта пустая → Bitmap Heap Scan.
  - После `VACUUM`: Index Only Scan, `Heap Fetches: 0`, 0.2 ms.
  - После `UPDATE` строк номера 42: `Heap Fetches: 3977` при 1991 строке — в индексе лежат записи и на старые (мёртвые),
    и на новые версии; каждую проверяли в таблице. Стало в 30 раз медленнее.
  - После повторного `VACUUM` — снова 0.
- **HOT update** (Heap-Only Tuple): если на той же странице есть место и изменённая колонка не входит ни в один индекс,
  новая версия пишется на ту же страницу и **индексы не трогаются**. Под это оставляют место настройкой `fillfactor`.
  Поэтому индексы на часто меняемые колонки особенно дорогие.

## 6. Транзакции

### ACID

- **Atomicity** — всё или ничего. Ошибка в середине → откат всего (`ROLLBACK`). Как `@Transaction` в Room.
- **Consistency** — ограничения (`not null`, `unique`, внешние ключи, `check`) всегда соблюдены.
- **Isolation** — параллельные транзакции не мешают друг другу; насколько — задаёт уровень изоляции.
- **Durability** — после `COMMIT` данные переживут падение сервера (сначала пишутся в журнал WAL).

### Аномалии

- **Dirty read** — видишь чужие **незакоммиченные** изменения. В Postgres не бывает никогда.
- **Non-repeatable read** — прочитал строку дважды в одной транзакции, получил разные значения: между чтениями кто-то
  закоммитил изменение (часть 1 лабы: 1000 → 700).
- **Phantom read** — повторил запрос с условием, появились **новые строки**.
- **Lost update** — две транзакции прочитали одно значение, обе записали, одна запись затёрла другую (часть 4: 900 вместо 600).
- **Write skew** — две транзакции читают общие данные, каждая меняет **свою** строку, и вместе они нарушают правило
  (классика: двое дежурных врачей одновременно снимаются с дежурства, каждый видит, что второй остаётся). Ловит только Serializable.

### Уровни изоляции в Postgres

- **Read Committed** (по умолчанию) — каждый **запрос** видит снимок на момент своего начала.
  Возможны non-repeatable read и phantom. `UPDATE` перед записью перечитывает **последнюю закоммиченную** версию строки —
  поэтому в части 3 на read committed итог правильный: 600.
- **Repeatable Read** — вся **транзакция** видит один снимок на момент первого запроса (часть 2: внутри всё время 1000).
  В Postgres тут нет и phantom read. Если пытаешься изменить строку, которую после твоего снимка изменил и закоммитил
  другой, — ошибка `could not serialize access due to concurrent update` (часть 3), транзакция откатывается целиком.
- **Serializable** — результат как будто транзакции шли строго по очереди. Postgres следит за зависимостями (SSI) и при
  нарушении отменяет одну транзакцию той же ошибкой сериализации. Ловит и write skew.
- Read Uncommitted в Postgres работает как Read Committed.
- Чем выше уровень — тем меньше аномалий, но тем чаще ошибки сериализации, и приложение должно уметь повторять.

### Что делать приложению при ошибке сериализации (SQLSTATE 40001)

- Это **временный** конфликт: данные целы, просто не повезло со временем.
- **Повторить всю транзакцию с начала**: заново прочитать, посчитать, записать. Повторить только упавший запрос нельзя —
  транзакция уже откатилась целиком.
- Повторять **ограниченно** (3–5 раз) с растущей паузой и случайным разбросом (exponential backoff + jitter).
  Не вышло — вернуть клиенту ошибку (409 Conflict или 503).
- Всё, что транзакция делает «наружу» (письмо, вызов другого сервиса), при повторе выполнится снова — поэтому такие
  действия делают после коммита или делают идемпотентными (Idempotency-Key из дня 3).
- Аналогия: retry с backoff на временную сетевую ошибку в OkHttp/WorkManager.

### Lost update: три способа защиты

1. **Атомарный UPDATE** — считать в базе, а не в коде: `update accounts set balance = balance - 100 where id = 1`.
   Чтение и запись в одной команде; на Read Committed UPDATE возьмёт последнюю закоммиченную версию.
   Самый простой и быстрый. Не подходит, если логику нельзя выразить одной командой.
2. **Пессимистичная блокировка** — `select balance from accounts where id = 1 for update` в начале транзакции.
   Строка «занята» до конца транзакции: другой, кто хочет её изменить или тоже взять `for update`, **ждёт**.
   После нашего `commit` он продолжит уже с новым значением → 600. Обычные `select` без `for update` не ждут (MVCC).
   Минусы: ожидание, риск deadlock. Аналогия: `synchronized`/`Mutex`, только на строку в базе.
   Когда: конфликты частые, операция короткая (списание денег, бронь последнего места).
3. **Оптимистичная блокировка** — колонка `version`:
   `update accounts set balance = 900, version = version + 1 where id = 1 and version = 5`.
   Если кто-то успел изменить строку, обновится **0 строк** → приложение понимает, что был конфликт, и повторяет или отвечает 409.
   Никого не блокирует. Так работает `@Version` в JPA (день 5). Аналогия: ETag/If-Match в HTTP, compare-and-set в `AtomicInteger`.
   Когда: конфликты редкие, между чтением и записью может пройти время (пользователь редактирует форму).

### Блокировки и deadlock

- `UPDATE`/`DELETE`/`SELECT ... FOR UPDATE` ставят блокировку на **строку** до конца транзакции. Читателей (обычный select) не блокируют.
- **Deadlock**: A заблокировал строку 1 и ждёт строку 2, B заблокировал строку 2 и ждёт строку 1. Postgres замечает это
  и отменяет одну из транзакций с ошибкой `deadlock detected` — её тоже нужно повторять.
- Профилактика: брать блокировки **в одном порядке** (например, по возрастанию id), держать транзакции **короткими**,
  не делать внутри транзакции сетевые вызовы и не ждать пользователя.

### Гонки (race condition) без явных транзакций

- «Вне транзакции» в Postgres не бывает: одиночный запрос без `begin` сам заворачивается в транзакцию (**autocommit**).
- Поэтому **один** запрос, даже долгий, атомарен и видит один снимок на момент своего начала — изменения,
  закоммиченные во время его работы, он не увидит; «половины старых, половины новых» данных не будет.
- Два запроса одновременно:
  - читают оба — не ждут друг друга (MVCC);
  - один пишет, другой читает — не ждут, читатель видит старую закоммиченную версию;
  - оба пишут в одну строку — второй **ждёт** блокировку, потом на Read Committed перечитывает новую версию строки
    и заново проверяет свой `WHERE`. Поэтому два `set balance = balance - 100` дают правильный итог;
  - два долгих UPDATE берут одни строки в разном порядке — возможен deadlock.
- Гонка случается **между** запросами из кода — **check-then-act**, как `if (!map.containsKey(k)) map.put(k, v)`
  без синхронизации в многопоточном Kotlin:
  1. **lost update** — прочитали, посчитали в коде, записали число (часть 4 лабы);
  2. **дубликат** — `select` «такого email нет» → `insert`; два параллельных запроса оба не нашли и оба вставили.
     Решение — `unique` в базе (+ обработка ошибки или `insert ... on conflict do nothing`). Проверка в коде — для красивого
     сообщения, гарантия — только в базе;
  3. **двойная бронь** (наш проект) — «номер свободен на эти даты?» → «да» → создаём бронь; два гостя одновременно получают «да».
     `unique` не поможет: пересекающиеся интервалы не «равны». Решения: `select ... for update` на строку номера
     (брони одного номера по очереди), Serializable + retry, или **exclusion constraint** — ограничение «никакие две брони
     одного номера не пересекаются по датам», которое база проверяет сама, как unique.
- **Главное правило: инварианты держит база, а не код.**
  - уникальность — `unique`;
  - счётчики и балансы — атомарный `update ... set x = x - 1`;
  - «прочитал → решил → записал» — `for update`, `@Version` или Serializable с повтором;
  - пересечение интервалов — exclusion constraint или блокировка.
