# День 5. Spring Data JPA, Hibernate, Flyway — конспект

## 1. Как Java-приложение вообще говорит с базой

Снизу вверх — каждый слой построен на предыдущем.

### 1.1. JDBC — «голый» доступ

- JDBC — стандартный Java API для любой SQL-базы. Для конкретной базы нужен **драйвер** (у нас `org.postgresql:postgresql`) —
  он знает сетевой протокол Postgres.
- Работа на JDBC выглядит так: взять соединение → подготовить SQL с параметрами `?` → выполнить → пройтись по `ResultSet`
  и руками достать каждую колонку (`rs.getString("guest_name")`) → закрыть всё в `finally`.
- Много однообразного кода, легко забыть закрыть соединение. Аналогия: разбирать JSON вручную через `JSONObject`.
- В Spring поверх JDBC есть `JdbcTemplate`/`JdbcClient` — убирает рутину, но SQL и маппинг по-прежнему твои.
  Это нормальный выбор для простых сервисов и сложных отчётов.

### 1.2. ORM — объекты вместо строк

- ORM (Object-Relational Mapping) — ты работаешь с **объектами**, а библиотека сама генерирует SQL и превращает строки в объекты.
- Проблема, которую решает ORM, называется *object-relational impedance mismatch*: в коде — объекты со ссылками
  (`booking.room.hotel`), в базе — плоские таблицы с внешними ключами. Кто-то должен переводить туда-обратно.

### 1.3. JPA — спецификация

- **JPA (Jakarta Persistence)** — это **стандарт**: интерфейсы и аннотации (`@Entity`, `@Id`, `@ManyToOne`, `EntityManager`,
  язык запросов JPQL). Сам по себе он ничего не делает — как интерфейс без реализации.
- Пакет `jakarta.persistence` (раньше `javax.persistence` — в старых статьях увидишь именно его).

### 1.4. Hibernate — реализация

- **Hibernate** — самая популярная реализация JPA, в Spring Boot — по умолчанию. Именно он генерирует SQL,
  кэширует объекты, следит за их изменениями.
- У Hibernate есть и свои возможности сверх стандарта (аннотации `org.hibernate.annotations.*`).

### 1.5. Spring Data JPA — репозитории без реализации

- Ты объявляешь интерфейс: `interface BookingRepository : JpaRepository<Booking, UUID>`.
- Spring при старте создаёт его реализацию (прокси) с готовыми методами: `save`, `findById`, `findAll(Pageable)`,
  `deleteById`, `existsById`, `count`…
- Можно объявлять методы по соглашению об именах — **derived queries**: `findByRoomIdAndCheckInBetween(roomId, from, to)` —
  Spring разберёт имя и сам построит запрос.
- Сложные запросы — через `@Query("select b from Booking b where ...")` (JPQL) или `nativeQuery = true` (чистый SQL).

### 1.6. Аналогия с Android

- JPA-аннотации ≈ аннотации Room (`@Entity`, `@PrimaryKey`).
- Hibernate ≈ код, который генерирует Room, но умнее и «живее» (см. persistence context).
- Spring Data репозиторий ≈ Retrofit-интерфейс или Room `@Dao`: объявил методы — реализация появилась сама.
- **Принципиальная разница:** Room — тонкая обёртка, всё явно: вызвал `update()` — получил UPDATE.
  Hibernate **управляет состоянием объектов**: загруженный объект «привязан» к сессии, и изменения в нём сами уходят в базу.
  Почти все ловушки JPA — отсюда.

## 2. Соединения и пул (HikariCP)

- Открыть соединение с Postgres дорого: TCP, TLS, аутентификация, а на сервере под каждое соединение стартует **отдельный процесс**.
- Поэтому приложение держит **пул** уже открытых соединений: взял на время транзакции → вернул.
  В Spring Boot пул по умолчанию — **HikariCP**, максимум по умолчанию — **10 соединений** (документация HikariCP).
  Аналогия: `ConnectionPool` в OkHttp.
- Связь с потоками: у Tomcat до **200** потоков, а соединений — 10. Если транзакции долгие, потоки стоят в очереди
  за соединением (по умолчанию ждут до 30 секунд, потом ошибка). Вывод: транзакции короткие, без сетевых вызовов внутри.
- Больше соединений — не всегда лучше: Postgres на каждое тратит память и процесс; у сервера обычно лимит ~100 соединений
  на **все** экземпляры всех сервисов. Пул подбирают под ядра базы, а не под число потоков приложения.

## 3. Сущность (`@Entity`)

### 3.1. Что это

- Класс, экземпляры которого Hibernate хранит в таблице: одно поле — одна колонка, один объект — одна строка.
- Обязательно: `@Entity` и поле с `@Id`. Имя таблицы — `@Table(name = "bookings")`, иначе возьмётся имя класса.
- Имена колонок Spring Boot по умолчанию переводит в snake_case: `guestName` → `guest_name`.
- `enum` храним строкой: `@Enumerated(EnumType.STRING)`. По умолчанию JPA пишет **порядковый номер** (ORDINAL) —
  вставишь новое значение в середину enum, и все старые данные «поедут». Классический вопрос.

### 3.2. Kotlin и JPA — три ловушки

1. **Конструктор без аргументов.** Hibernate создаёт объект через пустой конструктор, потом заполняет поля.
   В Kotlin его нет. Решение — плагин `kotlin("plugin.jpa")`: генерирует синтетический пустой конструктор для `@Entity`.
2. **Финальные классы.** Hibernate для ленивой загрузки создаёт **наследника** сущности (прокси — как в дне 2 со Spring AOP).
   Kotlin-классы по умолчанию `final`. Решение — `allOpen { annotation("jakarta.persistence.Entity") }`
   (плагин `plugin.spring` открывает только Spring-аннотации, `@Entity` в него не входит).
3. **`data class` — плохая идея для сущности.**
   - сгенерированные `equals/hashCode` берут **все** поля: объект поменял поле — и потерялся в `HashSet`;
   - `toString` трогает все поля, включая ленивые связи → лишние запросы или `LazyInitializationException`;
   - `copy()` создаёт новый объект, о котором Hibernate ничего не знает.
   Поэтому сущность — обычный `class` с `var`-полями, а `equals/hashCode` — по `id` (или не переопределять вовсе).

### 3.3. Генерация id

- `GenerationType.IDENTITY` — id назначает база (`bigserial`/`identity`). Минус: Hibernate обязан сделать INSERT сразу,
  чтобы узнать id, — **пакетная вставка (batch insert) отключается**.
- `GenerationType.SEQUENCE` — Hibernate заранее берёт числа из sequence (сразу пачкой), id известен до INSERT, batch работает.
  Для Postgres обычно лучший вариант для числовых id.
- `UUID` — можно генерировать в приложении (`UUID.randomUUID()`) или аннотацией `@GeneratedValue(strategy = GenerationType.UUID)`.
  Плюс: id известен сразу, не угадывается снаружи. Минус: 16 байт против 8 и случайный порядок вставки в индекс
  (UUIDv7, упорядоченный по времени, решает второе).

## 4. Persistence context — сердце JPA

### 4.1. Что это

- **Persistence context** (в Hibernate — `Session`, в JPA — за ним стоит `EntityManager`) — «рабочая область» Hibernate
  на время транзакции. В ней лежат все загруженные и сохранённые объекты.
- По умолчанию в Spring: **один persistence context на одну транзакцию**.
- Он даёт три вещи.

### 4.2. Кэш первого уровня и гарантия идентичности

- Внутри одного контекста `findById(x)` дважды вернёт **один и тот же объект** (`===`), а SQL выполнится один раз.
- Это не «кэш для скорости» между запросами — он живёт только до конца транзакции. Аналогия: локальная переменная, а не Redis.

### 4.3. Состояния сущности

- **Transient (новый)** — создан через конструктор, Hibernate о нём не знает.
- **Managed (управляемый)** — лежит в контексте: загружен через `find`/запрос или сохранён через `persist`.
  За ним Hibernate **следит**.
- **Detached (отсоединённый)** — контекст закрылся (транзакция кончилась), объект остался у тебя в руках. Изменения в нём
  никуда не уйдут; ленивые связи загрузить уже нельзя.
- **Removed** — помечен на удаление, DELETE уйдёт при flush.

### 4.4. Dirty checking — UPDATE без `save`

- Когда Hibernate загружает объект, он запоминает **снимок** его полей.
- Перед коммитом (при **flush**) он сравнивает каждый managed-объект со снимком и для изменённых генерирует `UPDATE`.
- Поэтому в транзакции достаточно `booking.status = CONFIRMED` — `save` не нужен. Новички пишут `save` по привычке из Room — это
  не ошибка, но показывает непонимание механизма.
- Обратная сторона: **случайно** изменил поле managed-объекта (например, «временно» для ответа) — оно уйдёт в базу.

### 4.5. Flush

- **Flush** — момент, когда Hibernate отправляет накопленные изменения SQL-командами в базу. Это **не** коммит: после flush
  транзакцию ещё можно откатить.
- Когда происходит: перед коммитом; перед JPQL-запросом, на результат которого могут повлиять несохранённые изменения;
  по явному `flush()`.
- Поэтому ошибка нарушения ограничения (например, `check`) часто вылетает не на строке `save`, а позже — при коммите.

### 4.6. `persist` против `merge` и «SELECT перед INSERT»

- `persist(new)` — сделать новый объект managed, при flush будет INSERT.
- `merge(obj)` — «у меня объект с id, синхронизируй»: Hibernate делает **SELECT** по id, копирует поля в managed-копию,
  потом INSERT или UPDATE.
- `JpaRepository.save()` выбирает сам: если сущность **новая** → `persist`, иначе → `merge`.
- Как Spring Data решает, что сущность новая (документация Spring Data JPA): если есть поле `@Version` не примитивного типа —
  новая, когда версия `null`; иначе — новая, когда **id равен `null`**. Можно переопределить через интерфейс `Persistable`.
- Следствие для нас: мы назначаем UUID в коде → id не `null` → Spring считает бронь «старой» → `merge` → **лишний SELECT
  перед каждым INSERT**. Увидишь это в логе на шаге 2 и починишь.

## 5. Связи между сущностями

### 5.1. Виды

- `@ManyToOne` — много броней → один номер. В таблице броней колонка `room_id` (внешний ключ). Самая частая и самая простая связь.
- `@OneToMany` — у номера список броней. Обычно это **обратная сторона** `@ManyToOne`: `@OneToMany(mappedBy = "room")`.
- `@OneToOne`, `@ManyToMany` (через промежуточную таблицу) — реже; `@ManyToMany` на практике часто заменяют явной сущностью-связкой.

### 5.2. Владеющая сторона

- Внешний ключ лежит в **одной** таблице. Сторона, где он лежит (`@ManyToOne`), — **владеющая**: только её изменения
  попадают в базу.
- `mappedBy` на `@OneToMany` значит «я только зеркало». Добавил бронь в `room.bookings`, но не выставил `booking.room` —
  в базе ничего не изменится. Поэтому двусторонние связи синхронизируют методами-хелперами (`room.addBooking(b)`).
- Совет: начинать с одной `@ManyToOne` и добавлять `@OneToMany`, только когда действительно нужно.

### 5.3. Cascade и orphanRemoval

- `cascade = [CascadeType.PERSIST, ...]` — операция над родителем распространяется на детей (сохранил заказ — сохранились строки заказа).
  Ставят **от родителя к детям**, никогда не на `@ManyToOne` (удалишь бронь — каскадом удалится номер).
- `orphanRemoval = true` — убрал ребёнка из коллекции родителя → DELETE.

## 6. Ленивая загрузка и N+1

### 6.1. LAZY и EAGER

- **EAGER** — связь загружается сразу вместе с сущностью. **LAZY** — вместо связи подставляется **прокси**, настоящий
  SELECT выполнится при первом обращении к полю.
- Значения по умолчанию в JPA: `@ManyToOne` и `@OneToOne` — **EAGER**, `@OneToMany` и `@ManyToMany` — **LAZY**.
- Общее правило: **все связи делать LAZY** (`@ManyToOne(fetch = FetchType.LAZY)`), а нужное подгружать явно в конкретном запросе.
  EAGER нельзя «выключить» для отдельного запроса — он грузится всегда.

### 6.2. LazyInitializationException

- Обратился к ленивой связи, когда persistence context уже закрыт (объект detached) — Hibernate не может выполнить SELECT
  → `LazyInitializationException: could not initialize proxy - no Session`.
- Типичный сценарий: сервис вернул сущность из `@Transactional`-метода, контроллер маппит её в DTO и трогает `booking.room.name`.
- Правильные решения: загрузить нужное **внутри** транзакции (JOIN FETCH / EntityGraph) или маппить в DTO внутри сервиса.

### 6.3. Open Session In View (OSIV) — почему `open-in-view: false`

- Spring Boot по умолчанию держит EntityManager открытым **на весь HTTP-запрос**, включая сериализацию JSON
  (`spring.jpa.open-in-view = true`, документация Boot) и пишет об этом предупреждение в лог.
- Плюс: `LazyInitializationException` «пропадает». Минусы:
  - ленивые SELECT-ы тихо выполняются из контроллера и Jackson — N+1 незаметно расползается;
  - соединение с базой может удерживаться дольше, чем нужно.
- Поэтому в серьёзных проектах ставят `false` и явно решают, что загружать. Мы так и сделали.

### 6.4. Проблема N+1

- Загрузили 20 броней одним запросом (**1**), потом в цикле для DTO обратились к `booking.room` у каждой — Hibernate сделал
  ещё **20** запросов (**N**). Итого 21 вместо 1–2. На списке в 1000 элементов — 1001 запрос.
- Почему опасно: на локальной базе незаметно (по 0.1 мс), на проде с сетевой задержкой и нагрузкой — секунды.
- Как обнаружить: логировать SQL (`org.hibernate.SQL: DEBUG`) и смотреть число запросов на один HTTP-вызов;
  в тестах — считать запросы (статистика Hibernate).
- Как решать:
  1. **`JOIN FETCH`** в JPQL: `select b from Booking b join fetch b.room` — один запрос с JOIN.
     С пагинацией по коллекциям (`@OneToMany`) осторожно: Hibernate может начать резать страницу в памяти.
  2. **`@EntityGraph(attributePaths = ["room"])`** на методе репозитория — то же самое без написания JPQL.
  3. **Batch fetching** (`hibernate.default_batch_fetch_size`) — вместо N запросов Hibernate сделает N/размер запросов с `where id in (...)`.
  4. **DTO-проекция** — выбрать сразу нужные поля в DTO (`select new ...` или интерфейс-проекция): без сущностей, без прокси.

## 7. Транзакции в Spring: `@Transactional`

### 7.1. Как работает

- `@Transactional` — это **прокси** (день 2!): Spring оборачивает бин, и перед вызовом метода прокси берёт соединение,
  делает `begin`, после метода — `commit`, при исключении — `rollback`.
- Отсюда ловушки дня 2:
  - **self-invocation**: вызов `this.otherMethod()` внутри того же класса идёт мимо прокси — `@Transactional` на нём не сработает;
  - метод должен быть доступен прокси (не `private`; в Kotlin класс открыт плагином `plugin.spring`).
- Где ставить: на **сервисе**, на методе бизнес-операции. Не на контроллере, не на репозитории (у методов Spring Data свои
  транзакции на каждый вызов).

### 7.2. Откат: какие исключения

- По умолчанию откат только на **unchecked** исключениях (`RuntimeException`, `Error`); на **checked** — коммит (документация Spring).
- **Ловушка Kotlin**: в Kotlin нет checked-исключений, но `IOException` и подобные **с точки зрения Spring** остаются checked.
  Бросил `IOException` из `@Transactional`-метода — транзакция **закоммитится**.
  Решения: `@Transactional(rollbackFor = [Exception::class])` или, начиная со Spring 6.2, глобально
  `@EnableTransactionManagement(rollbackOn = ALL_EXCEPTIONS)`.
- Исключение, пойманное **внутри** метода (`try/catch` без проброса), прокси не видит — отката не будет.

### 7.3. `readOnly = true`

- Подсказка, что транзакция только читает: Hibernate не делает снимки для dirty checking и не делает flush — меньше памяти и CPU.
  Драйвер может пометить соединение read-only. Для методов чтения — ставить.

### 7.4. Propagation — что делать, если транзакция уже есть

- **REQUIRED** (по умолчанию) — есть транзакция → присоединиться; нет → создать. Вложенный метод **разделяет** судьбу внешнего:
  исключение внутри помечает **всю** транзакцию на откат (`UnexpectedRollbackException`, если внешний его поймал и пытается закоммитить).
- **REQUIRES_NEW** — приостановить внешнюю, открыть **новую** (новое соединение из пула!), закоммитить независимо.
  Пример: запись в журнал аудита должна сохраниться, даже если основная операция откатилась.
  Риск: два соединения на один запрос — при маленьком пуле можно получить взаимную блокировку пула.
- **MANDATORY** (транзакция обязана быть), **SUPPORTS**, **NOT_SUPPORTED**, **NEVER**, **NESTED** (savepoint внутри той же транзакции) — реже.

### 7.5. Isolation

- `@Transactional(isolation = Isolation.REPEATABLE_READ)` — уровень изоляции из дня 4 для конкретной транзакции.
  По умолчанию — уровень базы (у Postgres — Read Committed). При Repeatable Read/Serializable не забыть повтор при ошибке сериализации.

## 8. Блокировки в JPA (связь с днём 4)

- **Оптимистичная** — поле `@Version` (`Long?`/`Int?`). Hibernate сам добавляет `where version = ?` в UPDATE и увеличивает версию;
  обновилось 0 строк → `OptimisticLockException` (в Spring — `ObjectOptimisticLockingFailureException`). Ответ клиенту — 409 или повтор.
  Бонус: nullable `@Version` заодно решает «SELECT перед INSERT» (см. 4.6).
- **Пессимистичная** — `@Lock(LockModeType.PESSIMISTIC_WRITE)` на методе репозитория → `select ... for update`.
- Ограничение: `@Version` защищает **одну существующую строку**. Двойная бронь — это два **разных INSERT**: версия тут не поможет.
  Нужны ограничение в базе (exclusion constraint), блокировка «родителя» (строки номера) или Serializable — см. конспект дня 4.

## 9. Миграции: Flyway

### 9.1. Почему не `ddl-auto`

- `spring.jpa.hibernate.ddl-auto`: `create`, `create-drop`, `update`, `validate`, `none`.
- `update` на проде не используют: не удаляет и не переименовывает колонки, не переносит данные, нет истории и ревью,
  результат зависит от текущего состояния базы.
- Правильно: схему меняют **миграции**, а Hibernate в режиме **`validate`** только сверяет сущности с таблицами — расхождение
  ловится при старте приложения, а не на первом запросе пользователя.

### 9.2. Как работает Flyway

- Миграции — SQL-файлы в `src/main/resources/db/migration`.
- **Версионные**: `V1__create_bookings.sql`, `V2__add_rooms.sql` — разделитель **два** подчёркивания. Применяются по порядку версий,
  каждая — один раз.
- **Повторяемые**: `R__views.sql` — применяются после версионных при каждом изменении файла (удобно для представлений, функций).
- При старте Flyway:
  1. создаёт (если нет) таблицу **`flyway_schema_history`** — журнал: версия, описание, контрольная сумма, кто и когда применил;
  2. сверяет контрольные суммы уже применённых файлов — **файл изменили → ошибка, приложение не стартует**;
  3. применяет новые миграции; у Postgres — каждая в своей транзакции (DDL в Postgres транзакционный — упала посередине → откат).
- Spring Boot запускает Flyway **до** Hibernate: сначала схема, потом проверка сущностей.

### 9.3. Правила работы с миграциями

- Применённую миграцию **не меняют** — пишут новую. (Локально, пока миграция никуда не ушла, можно пересоздать базу.)
- Непустая база без журнала Flyway → ошибка `Found non-empty schema(s) ... but no schema history table`.
  Для существующей продовой базы есть **baseline** (`baselineOnMigrate`) — «считать, что всё до версии N уже есть».
- **Миграции без простоя** (zero-downtime) на проде, где старая и новая версии сервиса работают одновременно:
  - переименование колонки = добавить новую → писать в обе → перенести данные → переключить чтение → удалить старую
    (подход *expand / contract*), растянуто на несколько релизов;
  - индекс на большой таблице — `create index concurrently` (день 4); но он не работает внутри транзакции — такую миграцию
    помечают как нетранзакционную;
  - `not null` на новую колонку большой таблицы — сначала колонка с default/nullable, заполнить, потом ограничение.
- Аналогия: `Migration(1, 2)` в Room + `exportSchema` в git. Разница — на бэкенде миграцию нельзя «откатить переустановкой приложения».
